# Butterfly 主题升级指南（P1 · 路径 C）

> **用途**：本项目对 `themes/butterfly/` 做了大量定制（自研页面壳、导航/页脚、评论、加载层等）。
> 升级 Butterfly 时**不能整目录覆盖**，必须按下表把定制文件搬回。
>
> **生成方式**：`node _snapshots\theme-inventory.js`（与 `node_modules/hexo-theme-butterfly/` 逐文件比对，
> **比对前已规范化 CRLF/LF 与末尾空白**，否则 git 的 autocrlf 会把"只差行尾"误报成"已改"）。
> **实测基线**（2026-09-11，Butterfly 5.7.0）：183 个文件 → **128 个与上游一致** / **32 个新增** / **23 个已改** / 1 个已删。
>
> 为什么不做"迁出 `themes/`"（原 4.9 方案的路径 A/B）：见文末「附录·为什么选择清单化」。

## 一、升级流程（按顺序）

```powershell
$demo = 'C:\Users\mabin\Desktop\web\demo'

# 1) 备份现状（含整个 themes 目录，保命）
robocopy $demo\themes "$env:USERPROFILE\Desktop\themes-backup-$(Get-Date -Format yyyyMMdd)" /E /R:2 /W:2

# 2) 提交当前工作区，确保有干净回退点
git -C $demo status --porcelain    # 应只有 data/music-playlist.json
git -C $demo add -A; git -C $demo commit -m "chore: before theme upgrade"

# 3) 升级版本
#    编辑 package.json:  "hexo-theme-butterfly": "5.7.0"  →  目标版本（去掉 ^ 以锁定）
npm install --no-audit --no-fund

# 4) 查看新主题改了什么（决定是否有需要适配的破坏性变更）
git -C $demo log --oneline -1
#    也可对比新旧包: npx --yes diff -r node_modules/hexo-theme-butterfly <旧备份>/node_modules/hexo-theme-butterfly
```

**5) 按下表把 55 个定制文件恢复**（第 2 节清单）。**关键：只覆盖表中列出的文件，不要动其他文件。**

```powershell
$new = "$demo\node_modules\hexo-theme-butterfly"   # 新版本
$old = "<上面第 1 步的备份>\demo\themes\butterfly"  # 旧定制版
# 对清单中每个文件执行（示例）:
Copy-Item "$old\layout\parts-common\footer.html" "$new\layout\parts-common\footer.html" -Force
```

**6) 处理已删文件**：`layout/includes/page/shuoshuo.pug` 在上游存在但本项目已删（本项目用自制 `moments.pug` 替代）。
升级后会被恢复，**建议再次删除**（保持与现状一致；留着也不影响构建，只是死代码）。

**7) 验证（必须全绿才收工）**

```powershell
cd $demo
npm run build            # hexo generate + minify + 冒烟(10 项)，失败即非零退出
npm test                 # 68 项单元测试
npm run verify -- --strict   # 18 项(结构 + 基线比对)
```

**判据**：`public/` **127** 文件 · `posts/` **15** 目录 · `search.xml` **149,662** · `sitemap.xml` **3,256** · `atom.xml` **10,927**
· 首页 LATEST SIGNAL `[文章] 绘世 Stable Diffusion @ 2026-09-03` · 精选工程顺序 `led-matrix → drone → line-car`

**8) 全站回归**：9 类页面各开一次（直接访问 + 站内 PJAX 跳转）
`/` `/articles/` `/articles/AI/` `/projects/` `/projects/led-matrix/` `/music/` `/moments/` `/about/` 任一文章页

## 三、升级后必查的 5 个易错点

| # | 检查项 | 怎么查 |
|---|---|---|
| 1 | **`inject.head` 的 vendor 引用仍在** | 产物首页应含 `/rose-galaxy/vendor/fontawesome/css/all.min.css`，且 **jsdelivr 引用 = 0** |
| 2 | **自定义 PJAX 实例仍在** | 产物应含 `/rose-galaxy/vendor/pjax/pjax.min.js`，且 `window.pjax` 存在（`_config.butterfly.yml` 的 `pjax.enable` 必须保持 **false**） |
| 3 | **`parts-common/*` 未丢** | `scripts/parts-common.js` 读取 8 个文件，缺任一即"整站壳断"；`npm run build` 会立刻报错 |
| 4 | **`//-` 注释没进 `script.` 块** | 在 pug 的 `script.` 块内写 `//-` 会**输出到产物 JS**（本项目踩过）；检查产物 HTML 中 `//-` 出现次数应为 0 |
| 5 | **`head.pug` 的 FontAwesome 是本地路径** | 新版主题可能把它改回 CDN，升级后要重新改本地（见 P0 改动） |

## 附录·为什么选择清单化（而不是把自制页迁出 `themes/`）

原方案 4.9 想让 `themes/butterfly/` 可被整包替换（迁出到 `scripts/pages/` 或 `layouts/`）。实测后放弃，原因：

1. **hexo 硬编码 layout 目录**
   `node_modules/hexo/dist/hexo/index.js:367` → `this.view_dir = path.join(theme_dir, 'layout') + sep`；
   而 `theme_dir = themes/<config.theme>`（`:128`）。**layout 必须在 `themes/<theme>/layout/`**，不可配置。
2. **view 注册机制不给外部挂目录**
   `theme/processors/view.js` 的 pattern 是 `layout/*path`；`theme.setView(path, data)` 的第二参是**文件内容**而非路径。用它绕开目录会打破 pug 的 `extends ./base.pug` / `include` 相对路径解析与 view 缓存。
3. **junction/symlink 方案会反向加重负担**
   要让 `themes/butterfly/layout` 指向外部目录，就必须把上游的 `layout/includes/`（104 文件）与 `_partials/` 一并复制进那个外部目录 —— 变成"维护上游 layout 的完整副本"，升级时要做 diff 合并，**收益从"整包替换"降级为"可 diff"**，并不优于清单化。
4. **本项目只有 55 个定制文件（144.7 KB）**
   清单化后升级动作是"拷 55 个文件 + 跑 3 条验证命令"，**约 5 分钟**；而迁移方案需 2–3 小时改造 + 全站回归，且引入符号链接的平台依赖。

**结论**：清单化以最小成本覆盖了"升级时知道该搬什么"这一核心收益。
